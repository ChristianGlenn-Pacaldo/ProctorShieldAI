# Production operations readiness

**State on 2026-09-30:** repository controls and dry-run tests exist, but no production cron services, offsite backup destination, alert receiver, or production restore drill has been configured or verified. This document is a deployment checklist, not evidence that those controls are live. The staging email waiver and disabled Resend choice are unchanged.

## Monitoring and operator response

Railway's `/api/health` deployment check gates startup; it is not a continuous uptime alert. The endpoint checks PostgreSQL, Redis, and private S3, returning only `200 {"status":"ok"}` or `503 {"status":"unavailable"}`. Server logs name the failing dependency without recording its URL or credentials. Railway captures resource metrics and searchable HTTP/deployment logs; application-level error-rate alerts require a separate monitor or log-query job. [Railway metrics](https://docs.railway.com/observability/metrics), [logs](https://docs.railway.com/observability/logs), and [alert options](https://docs.railway.com/guides/alerts-crashes-failed-deploys) describe their current scope. Assign a primary and backup on-call operator before launch.

| Signal | Automatic control to configure | Alert condition | Operator action |
| --- | --- | --- | --- |
| Web, PostgreSQL, Redis, private S3 | Poll `/api/health` over HTTPS every minute from outside Railway; keep the Railway deployment healthcheck | Three failures in five minutes, or any failed production deployment | Check the dependency label in web logs, Railway service state, and provider status; isolate the failed service and follow the incident steps below. |
| PostgreSQL/Redis capacity | Railway service CPU, memory, disk, restart and volume metrics; enable native monitors if the plan supports them | Disk/volume >80%; memory >85% or CPU >80% for 15 minutes; repeated restarts | Preserve logs, identify growth/connection pressure, scale or free capacity safely; never reset data to clear an alert. |
| Unexpected HTTP 5xx | Query Railway HTTP logs for `@httpStatus:500..599`, excluding expected controlled 503 maintenance/health incidents when triaged | Five errors in five minutes, or >2% of at least 20 requests | Group by route/request ID and deployed SHA; roll back compatible web code or apply a forward fix. |
| Maintenance | Railway cron exit status plus authenticated `GET /api/internal/maintenance` every 15 minutes | Last success >2 hours, HTTP 503, failed cron execution, or pending evidence media >=100 | Inspect cron/web logs; fix DB/S3 failure and rerun. The durable queue survives failed deletes and repeated runs are safe. |
| PayMongo webhook | Railway HTTP logs for `/api/billing/webhook` plus PayMongo delivery dashboard | Any repeated 5xx/503 or unresolved provider delivery failure after retry window | Check signature/mode settings and provider event ID; reconcile subscription/payment rows before manual retry. Never bypass signature or idempotency checks. |
| Offsite backup | Dedicated backup cron exit status and `backup-offsite.mjs --status` from an independent scheduled checker | Job nonzero, no successful set within 36 hours, or restore drill older than 30 days | Preserve failed job logs, fix destination/permissions/capacity, rerun a complete set, then test an isolated restore. |
| Evidence export completeness | Backup job compares active DB keys with source inventory and reads every encrypted destination object back before publishing `latest.json` | Any missing active key, changed/corrupt upload, or absent completion marker | Treat the set as incomplete; do not advance the recovery point. Investigate storage and retry from a coordinated window. |

**Current automation:** only Railway's existing deployment health gate and log/metric collection are active. The cron jobs, independent pollers, thresholds, recipients, and escalation routing above are **not configured**. Railway project webhooks report deployment status changes; they are not a substitute for health, backlog, payment, or backup freshness checks. Record a test alert delivered to both operators before production launch. Review HTTP 5xx and PayMongo delivery failures manually until the separate alert checks are live.

## Scheduled maintenance

The internal endpoint accepts only `POST` with `Authorization: Bearer <CRON_SECRET>`; `GET` with the same secret reports last successful run, pending deletion count, and attention status. Missing or short `CRON_SECRET` returns 503; invalid or missing bearer returns 401. No `NEXT_PUBLIC_*` value grants access. Keep the secret only in server/cron runtime variables, never in the browser bundle or deployment message. `POST` records a durable success timestamp **after** all maintenance work succeeds. Storage or final database failure leaves the evidence deletion marker for retry; a failed run does not advance the timestamp. Both methods return generic errors and logs omit provider exception text. `GET` returns 503 if the last success is more than two hours old or pending evidence media reaches 100 rows.

Create a separate, private Railway cron service from `Dockerfile.ops`, with no public domain, no healthcheck, and GitHub autodeploy disabled. Use UTC schedule `15 * * * *` and start command `node scripts/maintenance-cron.mjs`. Configure only `RAILWAY_ENVIRONMENT_ID` (supplied by Railway), `OPS_APPROVED_ENVIRONMENT_ID`, `OPS_APP_ORIGIN`, `OPS_APPROVED_APP_HOST`, and `CRON_SECRET`; target the approved production HTTPS origin. The runner exits nonzero on POST/GET failure and never prints the secret. Railway [cron jobs](https://docs.railway.com/cron-jobs) skip a scheduled execution if the prior process remains active, so alert on a stale status as well as failed executions. Run once manually against **staging only** with a staging secret and approved staging origin before creating the production schedule. A one-hour cadence normally drains up to 20 pending objects per run; increase frequency or process backlog manually if the queue grows.

## Offsite backup setup and execution

The source Railway evidence bucket has no native versioning, object lock, lifecycle policy, or bucket backup. [Railway bucket documentation](https://docs.railway.com/storage-buckets) lists those limitations. PostgreSQL volume snapshots and PITR may speed same-platform recovery, but a separately controlled logical dump and evidence export are required for project/account loss. [Railway's Postgres guide](https://docs.railway.com/guides/postgres-backups-restores) also recommends scheduled offsite logical dumps. No offsite provider or paid service is selected here.

`Dockerfile.ops` includes `pg_dump`, `pg_restore`, Node, and the backup scripts. The backup runner refuses any target except an explicitly approved Railway **production** environment and exact PostgreSQL host/database. It also refuses a destination on the source S3 endpoint, reused bucket/credentials, malformed HTTPS endpoint, missing 32-byte AES-256 key, or an unconfirmed coordinated write/maintenance pause. It never reads `.env` automatically. Required private runtime variables:

| Purpose | Variables |
| --- | --- |
| Source guard | `BACKUP_TARGET_ENV=production`, Railway-supplied `RAILWAY_ENVIRONMENT_NAME=production`, `RAILWAY_PROJECT_ID`, `RAILWAY_ENVIRONMENT_ID`, matching `BACKUP_APPROVED_PROJECT_ID`/`BACKUP_APPROVED_ENVIRONMENT_ID`, `BACKUP_APPROVED_DATABASE_HOST`, `BACKUP_APPROVED_DATABASE_NAME`, `BACKUP_APP_COMMIT` (exact 40-character deployed web SHA) |
| Source access | `DATABASE_URL`, `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`; optional `S3_REGION`, `S3_FORCE_PATH_STYLE` |
| Independent destination | `BACKUP_DESTINATION_ENDPOINT`, `BACKUP_DESTINATION_BUCKET`, `BACKUP_DESTINATION_ACCESS_KEY`, `BACKUP_DESTINATION_SECRET_KEY`; optional `BACKUP_DESTINATION_REGION`, `BACKUP_DESTINATION_FORCE_PATH_STYLE`, `BACKUP_DESTINATION_PREFIX` (default `proctorshieldai`) |
| Encryption and window | `BACKUP_ENCRYPTION_KEY` (base64, 32 random bytes), `BACKUP_WRITES_PAUSED=true`, `BACKUP_MAINTENANCE_PAUSED=true` **only while a verified pause is active** |

Do not set these as `NEXT_PUBLIC_*` values or Docker build arguments. Store the encryption key in a separately controlled secret store, with a recovery copy accessible to the backup operator; losing the key makes all sets unreadable. Use an approved encrypted runner disk because temporary files and a later restore may contain sensitive data. The backup runner writes temporary **encrypted** files only under ignored `.data/ops-backups/`, deletes them at completion/failure, and never commits media or dumps.

1. Select an independent private bucket/account with TLS, access controls, encryption at rest, versioning or immutability where available, and a documented 30-day lifecycle/rotation policy. Approve its cost and credentials before configuration. Separate source read permission from destination write/read permission.
2. Establish a real coordinated write and maintenance pause for the backup window; the two environment flags are operator assertions, **not a technical pause mechanism**. The intended daily UTC backup schedule is `0 2 * * *` after that pause is enforceable. A routine cron with those flags permanently set would be unsafe. Record the pause start/end and actual recovery point. Until this is implemented, run the helper only in a controlled window and call backups manual.
3. Run `node scripts/backup-offsite.mjs --check-config`, then `node scripts/backup-offsite.mjs --backup` in the guarded job. It streams a custom-format PostgreSQL dump into AES-256-GCM, checks it with `pg_restore --list`, inventories private `evidence/` objects, confirms all active DB evidence keys are present, exports each object encrypted, and downloads every uploaded ciphertext for SHA-256 verification. An encrypted manifest records the approved web SHA, applied migration names, and private key mapping. `latest.json` is written **last**, only after all checks pass. A partial failed set never advances the success marker.
4. Schedule `node scripts/backup-offsite.mjs --status` independently at least every six hours (`0 */6 * * *` UTC), with a separate alert receiver that also detects a missed checker run. The checker needs the approved Railway project/environment IDs and **read-only destination credentials**; it does not need source database/S3 access or the encryption key. It exits nonzero when the latest complete set is older than 36 hours or `restore-status.json` records no isolated restore verification within 30 days. Route nonzero exits and missed runs to both operators. `restore-status.json` at the destination prefix has the form `{"verifiedAt":"<UTC ISO timestamp>","setId":"<tested set ID>"}` and must be updated **only after** an actual isolated PostgreSQL-and-evidence restore drill; archive the drill evidence and reviewer sign-off. A mere download or archive listing is not a restore drill.
5. Test retention/rotation in the destination account. Do not delete the last known-good set after a failed run. Confirm old data, including expired evidence, is removed from the backup destination according to the approved retention/privacy policy.

The recovery set format is `sets/<set-id>/database.bin`, `manifest.bin`, indexed encrypted evidence objects, and `completion.json`. Each encrypted file is 12-byte IV, AES-256-GCM ciphertext, then 16-byte tag. The per-set completion record retains the encrypted manifest SHA-256 even after `latest.json` advances to a newer set; neither record contains credentials or private evidence keys. The separate `scripts/backup-restore.mjs --verify-only <set-id>` helper downloads, authenticates, decrypts, and checks the archive and every object in an ignored temporary directory, then removes it. Set `RESTORE_TARGET_ENV=isolated`, destination credentials/key, prefix, and `RESTORE_MANIFEST_SHA256` from that set's protected `completion.json`. If running under Railway, use a separate environment named `recovery`; the helper rejects other Railway environments. Use `--download <set-id>` only on an approved encrypted recovery runner; it retains a decrypted `database.dump`, `manifest.json`, and indexed evidence files under `.data/ops-restore/<set-id>/`. This helper **does not** restore to any database or bucket. Follow the isolated restore and reconciliation sequence in [the staging recovery runbook](railway-staging-runbook.md), using new resources and never the live database. Destroy decrypted working files after verification.

## Incident decisions

| Incident | First action | Recovery choice |
| --- | --- | --- |
| Unhealthy web deploy | Stop traffic/cutover, inspect exact SHA, health dependency label and deployment/HTTP logs | Roll back a retained compatible web image; if schema changed incompatibly, apply a forward fix. A web redeploy does not restore data. |
| Redis outage | Confirm Redis service/restarts/network and health 503; preserve session/rate-limit impact | Restart/repair Redis or restore its service/volume as approved. Keep web health failing until shared state works; do not silently switch to process-local state. |
| PostgreSQL outage | Stop writes, preserve logs and latest backup/PITR point, confirm service/volume state | Restore into a new isolated DB from PITR/snapshot or verified logical set; reconcile migrations/data before cutover. Never run `db push` or reset on live data. |
| Private S3/evidence outage | Stop evidence-dependent flows and retention cleanup; inspect bucket credentials, permissions and provider state | Repair provider access or restore verified objects to a new private bucket; reconcile every active DB key and authorized read. Missing media should return controlled 503. |
| Bad migration | Stop the web rollout and writes; preserve the pre-migration recovery set and inspect applied SQL | Prefer forward fix for compatible partial migrations. Restore coordinated DB/evidence set to new resources only when forward repair is unsafe; web rollback alone does not reverse schema. |
| Failed PayMongo webhook | Preserve event ID and HTTP/provider delivery status; check signing mode, provider response and DB transaction logs | Fix root cause and let provider retry; reconcile payment/subscription idempotency before any controlled replay. Do not create live charges or bypass signature checks. |
| Failed/stale backup | Keep prior good set and logs; verify destination, key availability, capacity, manifest and last marker | Retry a full set after repairing the fault. If no good set meets the recovery objective, declare the gap and prioritize an isolated restore test; never treat local `.data` as an offsite backup. |

After any incident, record timeline, affected set/commit, data gap, restore evidence, customer impact, and the change that prevents recurrence. Verify `/api/health`, maintenance status, private evidence reads, payment state, and HTTP 5xx before reopening traffic.

## Production launch gate

Production operations are **not ready** until the independent destination and retention policy are approved/configured, coordinated backup pause is enforced or replaced by a proven consistent online method, daily job and independent freshness/alert checks are scheduled, an isolated restore of an encrypted set passes, on-call alert delivery is tested, and the maintenance cron has passed staging verification. None of these configuration steps is performed by this repository change.
